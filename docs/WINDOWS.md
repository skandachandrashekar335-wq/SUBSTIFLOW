# Windows Compatibility

SubstiFlow is an Electron + React + TypeScript + SQLite desktop app. This
document records what has and has not been verified about running it on
Windows, and how the Windows checks are automated. It is deliberately strict
about the difference between *packaging* a Windows installer and *running* the
application on Windows.

## Evidence levels (read this first)

| Level | What it means | Status |
|---|---|---|
| 1. Static inspection | Packaging config, runtime code, paths, native-module story reviewed for Windows portability | **Done** — findings below |
| 2. Cross-packaging on macOS | `npm run dist` on the macOS dev host produces a real Windows NSIS installer | **Done** — verified today (`dist-electron/SubstiFlow-Setup.exe`, 83,617,673 bytes, PE32 NSIS; `win-unpacked/` inspected — `app.asar` 1.6 MB with only `better-sqlite3` + its chain, native module is PE32+) |
| 3. Windows runner automation | `.github/workflows/windows-compatibility.yml` runs install → tests → typechecks → build → NSIS package → artifact upload on `windows-latest`, plus an experimental GUI smoke job | **Prepared, not yet executed** — the workflow files are local and uncommitted; nothing has run on a hosted Windows runner |
| 4. Manual desktop test | A person installs and uses the packaged app on an actual Windows machine | **Not done** — required before claiming Windows support |

Until levels 3 and 4 have actually happened on Windows, Windows compatibility
is **unverified**. A green build of level 2 on macOS proves the packaging
pipeline, not the runtime.

## 1. Packaging audit (`package.json` → `build`)

- **NSIS installer**: `win.target = nsis`, `arch = [x64]` (matches the
  x64 Electron and the x64 better-sqlite3 prebuild; Windows-on-ARM devices
  run it via x64 emulation, 32-bit Windows is not targeted).
- **Installer UX**: `oneClick: false` (shows a real install wizard),
  `perMachine: false` (per-user install, no admin rights needed),
  `allowToChangeInstallationDirectory: true`, `createDesktopShortcut: true`,
  `createStartMenuShortcut: true`. The NSIS target always embeds an
  uninstaller and an Add/Remove Programs entry; `deleteAppDataOnUninstall`
  is left at its default (`false`), so **user data in
  `%APPDATA%\SubstiFlow` survives uninstall**.
- **Icon**: `public/icon.ico` is generated by `npm run icon`
  (`scripts/make-icon.js`) with 16/32/48/64/128/256 px PNG-compressed
  entries — electron-builder's 256 px requirement is met (packaging
  succeeds without icon errors).
- **Files packed**: `dist/main/**`, `dist/renderer/**`, `package.json`, plus
  electron-builder's automatic production-dependency closure. Verified inside
  `win-unpacked/resources/app.asar`: `dist/main/electron/main.js`,
  `dist/main/electron/preload.js`, `dist/main/src/db/migrations.js`,
  `dist/main/src/db/nodeDb.js`, `dist/main/src/db/schema.sql`,
  `dist/renderer/index.html` + assets, `package.json`, and production
  `node_modules` are all present.
- **Native module**: `asarUnpack: node_modules/better-sqlite3/**` — verified:
  `app.asar.unpacked/.../better_sqlite3.node` is a `PE32+ executable (DLL)
  x86-64` (Windows). `npmRebuild: false` is safe because `predist` runs
  `node scripts/ensure-abi.js win32`, which downloads the published
  **win32-x64 prebuild for Electron 31's ABI** before packaging. The same
  script works natively on a Windows machine.
- **No publish side effects**: electron-builder only publishes when an
  explicit `--publish` policy is given; `npm run dist` does not pass one and
  the CI job receives no `GH_TOKEN`.
- Known cosmetic nit: `app.asar.unpacked` also contains
  `test_extension.node`, a macOS Mach-O test fixture of better-sqlite3 that
  rides along from `node_modules`. Nothing loads it at runtime; it only adds
  a few KB.

## 2. Runtime-code portability

- **Paths**: `electron/main.ts` and `src/db/nodeDb.ts` use `path.join` /
  `path.dirname` and `fs` exclusively — no hardcoded `/` or `\`. The
  production renderer loads via `loadFile(path.join(__dirname,
  '../../renderer/index.html'))`, which is `file://`-safe on Windows.
- **User data**: `app.getPath('userData')` with `app.setName('SubstiFlow')`
  resolves to `%APPDATA%\SubstiFlow` on Windows (per-user, correct location);
  the database lives in `<data>/database/substiflow.db` with automatic
  daily backups under `<data>/database/auto-backups/`. The
  `SUBSTIFLOW_DATA_DIR` override (used by every test harness) is honored on
  all platforms.
- **No shell commands in runtime code**: the main process, preload and
  renderer never spawn processes or call shells; only build-time helper
  scripts do, and those are Windows-aware (`ensure-abi.js` passes
  `shell: process.platform === 'win32'`; `postinstall.js`'s `codesign`
  step is guarded by `process.platform === 'darwin'`).
- **Database**: WAL journal + foreign keys via pragmas — portable. Hot
  backup uses better-sqlite3's `.backup()` API (no file copying of a live
  database); import closes the database before `copyFileSync` and re-runs
  migrations on the imported file's version.
- **Window lifecycle**: `window-all-closed` quits on non-darwin platforms —
  on Windows, closing the window exits the app as users expect.
- **Single instance**: there is **no** `requestSingleInstanceLock()`. Two
  launches mean two processes on one SQLite database (WAL tolerates this,
  but backup/import flows get confusing). This is a pre-existing,
  platform-neutral gap; it was left unchanged because fixing it would alter
  working macOS behavior beyond the reported issues.
- **Offline-first**: the renderer CSP allows only `self`/`ws:`/localhost
  connections; no `fetch`/XHR to external hosts exists in `src/`. The E2E
  harness now records every request the app makes and fails if any http(s)
  URL is not localhost — last run: **0 external requests** across all
  journeys.

## 3. Path checks (separators, spaces, permissions)

- Static: everything goes through `path.join` (above).
- Runtime check (isolated, temp directory, ad-hoc script): launched the
  production build with
  `SUBSTIFLOW_DATA_DIR="/…/T/substiflow space test <ts>"` (spaces in every
  segment). Result: DB created (430 KB after migrations), schema stamped
  **v8**, first-run wizard rendered — **PASS**. On Windows the same override
  lands under `%TEMP%`; the harness itself builds QA directories from
  `os.tmpdir()`, which is portable.
- Directory creation uses `fs.mkdirSync(..., { recursive: true })`, which is
  permission-safe on Windows per-user locations.

## 4. E2E harness portability (`scripts/e2e/journeys.js`)

- **Fixed a genuine portability bug**: stale-process cleanup used `pkill`,
  which does not exist on Windows. It is now `killStaleElectron()`: on
  win32 it runs PowerShell (`Get-CimInstance Win32_Process` → filter
  `electron.exe` whose executable path is under this checkout's
  `node_modules/electron/dist` → `Stop-Process`), spawned with an argv array
  so cmd.exe quoting never applies; other platforms keep `pkill -f <abs
  path>`. Both variants only ever kill Electron started from this checkout.
- Already portable (verified, unchanged): `execSync('npm run build')` uses
  cmd.exe on Windows; `require('electron')` resolves `electron.exe`, which
  Playwright launches directly; ABI stamping runs `node`/`npm` from PATH;
  QA dirs and screenshots live under `os.tmpdir()`.
- **Journey H added** so the Windows smoke checklist is covered by the same
  suite on any platform: an explicitly configured **multi-teacher TEAM lab**
  (span 2, both teachers on the session) and an **ALTERNATE** requirement on
  the same subject (exactly one teacher per session, both teachers used),
  generated by the real solver and independently validated. Journey order:
  A, F, B, C, H, then relaunch sessions D/E/G1 and G2 (H runs after B,
  which needs the requirement table to hold exactly one row while it edits).
- Full checklist mapping (what a Windows smoke run exercises): fresh
  `SUBSTIFLOW_DATA_DIR` + migrations → first-run wizard → subject &
  teaching-faculty creation → non-teaching staff excluded from allocation
  and substitution → TEAM lab + ALTERNATE → generate/validate/publish →
  relaunch persistence + auto backup → attendance → substitution approval →
  offline assertion.

## 5. Workflow

`.github/workflows/windows-compatibility.yml` (separate from the macOS
`ci.yml`):

1. `windows-verify` (blocking): checkout → Node 20 → `npm ci --ignore-scripts` →
   Electron runtime/native prebuild preparation → `npm test` → `npx tsc --noEmit` → `npx tsc -p tsconfig.electron.json --noEmit` →
   `npm run build` → `npm run dist` (NSIS) → assert
   `dist-electron\SubstiFlow-Setup.exe` exists and is ≥ 10 MB → upload the
   installer (+ `latest.yml`) as a workflow artifact for manual testing on
   a real Windows desktop.
2. `windows-runtime-smoke` (experimental, `continue-on-error: true` until
   observed green): `npm run e2e` — the full GUI journey suite against the
   real app on the Windows runner, isolated database. **A green workflow
   status does not mean this job passed; its log must be read.**

## 6. Still requires a real Windows desktop

- Installing and launching `SubstiFlow-Setup.exe` (SmartScreen shows a
  "Windows protected your PC" warning for unsigned installers — expected
  until code signing exists).
- Installer shortcuts, uninstall, and per-user install without admin.
- Native backup export/import dialogs.
- Antivirus false-positive heuristics (not observable from CI or macOS).
- WAL file behavior on NTFS under real multi-day use.
